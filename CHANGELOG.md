# Bitrate — Product Changelog

Product-level release history. Each per-package `CHANGELOG.md` (`apps/*/CHANGELOG.md`,
`packages/*/CHANGELOG.md`) is generated by `changeset version` and lists that package's own
changes in detail; this file tracks the product version itself, from `package.json`, and calls
out anything that affects how the release history as a whole should be read.

## v0.2.0

Reset the product version scheme from `1.x` back to `0.x`. The product isn't launched yet — it's
still under active development and the UI runs an unofficial design lifted from Spotify — and a
`1.x` version implies a stable, shipped release, which semver's own convention reserves `0.y.z`
to signal is not yet the case.

Tags `v0.0.1`, `v1.0.0` and `v1.1.0` predate this reset and stay published as-is: git tags and
the GHCR images they point at are treated as immutable once released, and nothing in the
release/deploy pipeline resolves "current" by comparing tag numbers — `release_publish.yml`
always tags and publishes exactly the version in the merged tree, and `deploy.yml` always
deploys an explicitly named tag, never "the highest semver tag." The one visible side effect is
cosmetic: a release's "Changes since `<tag>`" note may name a numerically higher pre-reset tag as
its predecessor, and anyone comparing tags by eye will see `v1.1.0` sort above `v0.2.0`/`v0.3.0`
— both are artifacts of the reset, not a sign that history was rewritten or that a later release
is somehow "older."

Per-package versions (`@bitrate/api`, `@bitrate/admin`, `@bitrate/web-player`, etc.) are
unaffected by this reset; they continue independently from wherever `changeset version` had
already brought them.
