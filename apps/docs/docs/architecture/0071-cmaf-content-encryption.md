# ADR-0071: CMAF content encryption — one `cbcs` packaging, keys only for a live play session

Status: Proposed — when accepted, it supersedes "DRM is out of scope" in
[ADR-0065](./0065-single-cmaf-aac-delivery-format.md) and the matching consequence of
[ADR-0067](./0067-playback-sessions.md)

Date: 2026-11-10

Tracked in [#522](https://github.com/Lordpluha/bitrate/issues/522).

## Context

After ADR-0065 and ADR-0067 listener audio leaves the API only through
`GET /tracks/:id/cmaf/:bitrate`, authorised by a per-play session token and paced to real time.
The bytes themselves are plain AAC-LC in fMP4: any response captured from the network panel, the
browser's disk cache or a proxy is a playable file. Pacing makes a rip slow, not useless.

Two pressures make encryption a durable decision rather than a hardening detail:

- **Label catalogue.** Licences from majors and most distributors require DRM for subscription
  streaming, usually with named systems (Widevine, FairPlay, PlayReady) and a minimum security
  level per tier. Without a plan for it Bitrate cannot sign such a deal.
- **Artist expectations.** Independent artists upload their own masters; a public link that saves
  as a file undermines a paid tier even without a label contract.

What already constrains the design:

- `@bitrate/player` plays CMAF through MSE and, without MSE, the same `.m4a` through a native
  `<audio>` (ADR-0065 D3). It does not route audio through WebAudio, so Encrypted Media Extensions
  (EME) fit the existing pipeline.
- Renditions are addressed by byte ranges from a database index (ADR-0020). Encryption must not
  change the fragment grid or the alignment between renditions (`assertAlignedRenditions`).
- Browsers differ: Chromium and Firefox implement the `org.w3.clearkey` key system; WebKit (Safari,
  iOS, and WKWebView inside Tauri on macOS) supports only FairPlay through EME. Linux Chromium
  builds and WebKitGTK may ship no Widevine CDM at all.
- No absolute protection exists: decoded audio can always be recorded from the output. The goal is
  to make saving the delivered bytes useless and to meet licence terms.

## Decision

**One packaging: CMAF Common Encryption with the `cbcs` scheme.** The worker encrypts every
rendition in the same FFmpeg/packager pass that produces it today. `cbcs` (AES-128-CBC, ISO/IEC
23001-7) is the one scheme all three commercial DRM systems decrypt, so the stored files never need
repackaging when a DRM system is added. Encryption keeps the fragment boundaries; the byte index in
`TrackFile.fragments` is computed from the encrypted output, and alignment checks run on it.

**One key per track.** All renditions of a track share one content key and key ID (KID); a new
generation (re-upload) gets a new key. Keys are generated by the worker, stored envelope-encrypted
under a key-encryption key supplied from the environment (never in the database or the repository),
and are readable only by the key service, not by any listener or artist route.

**Keys are released only against a live play session.** A key endpoint under the existing session,
`POST /tracks/:id/play-sessions/:sid/key`, verifies the ADR-0067 token, checks the Redis session is
alive and the track matches, and returns the key in the format the client's key system expects.
Revocation and session limits therefore apply to keys exactly as they apply to bytes. Key responses
are `Cache-Control: no-store`.

**Two phases behind one server contract.**

- **Phase A — clear-key, no vendor.** Chromium and Firefox use EME `org.w3.clearkey`; Android uses
  Media3 ClearKey. The key endpoint answers with a JSON Web Key set. This stops saving the delivered
  bytes as a playable file, at no licence cost. A determined attacker can still read the key in the
  page, which is accepted for independent-artist content.
- **Phase B — multi-DRM through a licence provider.** When a label agreement requires it, the key
  endpoint becomes a licence proxy to a multi-DRM provider (Widevine, FairPlay, PlayReady). The
  stored `cbcs` files, the key IDs and the session checks stay; only the response format and the
  player's key-system configuration change. The provider is chosen by a separate ADR.

**Clients without a usable key system.** Until Phase B, WebKit and any client whose EME offers no
supported key system play through the native path. For them the worker keeps one **unencrypted
128 kbps** rendition, served through the same session, pacing and limits. Higher qualities exist
only encrypted. Phase B removes the unencrypted rendition once FairPlay covers WebKit.

**Ownership.**

| Concern | Owner |
|---|---|
| Key generation, packaging, KID in the init segment | worker (`apps/api` processing) and `@bitrate/converter` |
| Key storage and envelope encryption | API key service |
| Key release, session checks, revocation | `PlaybackSessionService` + key endpoint |
| Key-system selection, EME session, licence requests | `@bitrate/player` engine, behind its contract |
| Supplying session token and key URL | hosts (web-player, desktop, mobile) through the player contract |

## Consequences

- A saved response or cached file no longer plays without a key obtained through a live session.
- Every play makes one extra request (the key) before the first audio; the player can request it in
  parallel with the init segment, and the next track's key is prefetched with its session.
- Storage grows by one 128 kbps rendition per track until Phase B.
- The admin preview (`/admin/tracks/:id/audio`) needs either the unencrypted rendition or its own
  staff key path; it must not reuse listener sessions.
- Gapless or crossfade through WebAudio becomes impossible for encrypted audio; any future work on
  them must stay on MSE or `<audio>`.
- Losing the key-encryption key makes every encrypted track unplayable; its backup and rotation
  are part of the operations runbook before Phase A ships.
- Phase A is not DRM in the licensing sense; label content requires Phase B.
- Out of scope: forensic watermarking, offline downloads, device attestation (Play Integrity, App
  Attest), the choice of DRM vendor.

## Alternatives considered

- **HLS AES-128 (whole-segment encryption)** — simple, but ADR-0065 removed HLS, and the scheme is
  not decryptable by Widevine or PlayReady, so Phase B would repackage the catalogue.
- **`cenc` (AES-CTR) scheme** — supported by Widevine and PlayReady but not by FairPlay; two
  packagings instead of one.
- **Decrypting in JavaScript before `appendBuffer`** — works without EME on every MSE browser, but
  exposes decrypted bytes and the key to page scripts, and cannot help the native `<audio>` path.
- **Encrypting on the fly in the API** — avoids re-encoding, but rewrites `moof`/`senc` boxes per
  response, breaks the stored byte index and costs CPU on every request.
- **Commercial multi-DRM from day one** — strongest, but costs per licence and couples the first
  release to a vendor before any label deal requires it; the `cbcs` packaging keeps this path open.
- **Keep audio unencrypted** — the status quo of ADR-0067; acceptable only while no licence or
  artist requires more than pacing.
